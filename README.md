- **A critical prompt-injection-to-RCE flaw in the Langroid LLM-agent framework (CVE-2026-25879, CVSS 9.8) keeps the agentic SQL attack surface in the spotlight** -- A newly published advisory pins a CVSS 9.8 critical rating on CVE-2026-25879 in Langroid, a popular open-source framework for building LLM-powered applications. The flaw lives in Langroid's SQLChatAgent, which executes SQL produced by the model - and because that SQL is steerable by prompt injection, an attacker who can shape the agent's input (directly via a malicious prompt, or indirectly by poisoning data the model later reads) can coerce dangerous, dialect-specific primitives. When the agent connects with a database role that has elevated privileges such as PostgreSQL `pg_execute_server_program`, MySQL `FILE`, or MSSQL `xp_cmdshell`, those primitives (for example `COPY ... FROM PROGRAM`) escalate from data theft to full remote code execution on the database host, per the [GitLab Advisory Database - CVE-2026-25879: Langroid has Prompt to SQL Injection, Leading to RCE](https://advisories.gitlab.com/pypi/langroid/CVE-2026-25879/). The fix landed in Langroid 0.63.0, which now defaults SQLChatAgent to a SELECT-only allowlist parsed with sqlglot plus a dialect-aware dangerous-pattern blocklist, per the maintainer's [GitHub Security Advisory - Prompt to SQL Injection leading to RCE in Langroid (GHSA-mxfr-6hcw-j9rq)](https://github.com/langroid/langroid/security/advisories/GHSA-mxfr-6hcw-j9rq). The pattern is the through-line for agentic AI security right now: the same text-to-SQL-to-database path produced the actively exploited LiteLLM proxy injection (CVE-2026-42208), where a crafted Authorization header reached an unparameterized key-lookup query through the error-handling path - fixed in v1.83.7 and recommended at v1.83.10-stable, per the [LiteLLM docs - Security Update: CVE-2026-42208 in LiteLLM Proxy](https://docs.litellm.ai/blog/cve-2026-42208-litellm-proxy-sql-injection). The lesson both flaws underline is that any LLM allowed to author SQL must run against a least-privilege, read-only-by-default database role, because the model's output has to be treated as untrusted attacker-controllable input.
