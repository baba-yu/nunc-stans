- **MosaicQuant splits weights into a dense plus sparse 4-bit pair to keep near-FP16 accuracy** — A paper posted to arXiv on June 14 (arXiv:2606.15652, cs.LG and cs.CL) proposes MosaicQuant, a 4-bit large-language-model quantization scheme aimed at the tension between compressing the dense bulk of a weight matrix and faithfully preserving the rare large-magnitude outliers that 4-bit grids tend to clip. Rather than fall back on a mixed-precision format, MosaicQuant disaggregates each weight matrix into a dense 4-bit base component that captures most values and a sparse 4-bit residual component that compensates for quantization error in the most error-sensitive blocks, so both pieces stay in 4-bit. To keep that two-part representation from re-introducing the overhead mixed-precision methods usually pay, the authors add ZipperEngine, which folds the sparse residual computation into the dense 4-bit matrix operations through an overlapped pipeline, preserving a unified low-bit execution path. On LLaMA3 and Qwen3 models the method is reported to retain near-FP16 accuracy while delivering up to a 1.24x speedup over the 16-bit baseline. As with any single-paper result the numbers are the authors' own and await independent reproduction and broader model coverage, but the work is a concrete data point in the effort to make 4-bit serving the default for memory-constrained local deployment rather than a lossy fallback. [arXiv:2606.15652 - MosaicQuant: Inlier-Outlier Disaggregation for Unified 4-Bit LLM Quantization](https://arxiv.org/abs/2606.15652)

- **Vertex AI SDK cross-tenant RCE via staging-bucket squatting** — Palo Alto Networks' Unit 42 published a writeup on June 16 detailing a cross-tenant remote-code-execution chain it calls "Pickle in the Middle," affecting Google Cloud's Vertex AI SDK for Python (versions 1.139.0 and 1.140.0). The flaw combined two weaknesses: when a developer did not specify a staging bucket, the SDK minted a deterministic default name from the pattern project-id-vertex-staging-region, and it then checked only that such a bucket existed, not that the caller actually owned it. An attacker who knew a victim's project ID could pre-create that bucket in their own account (bucket squatting), silently capturing the victim's model upload and swapping in a poisoned artifact. Because most Vertex models are serialized with pickle or joblib, a crafted object's __reduce__ method runs arbitrary code the instant the model is deserialized inside Google's serving container, before any validation. The payload then lifts an OAuth token from the container's metadata server, yielding a service account with cloud-platform scope and access to other deployments and BigQuery metadata. Unit 42 reported the issue through Google's Vulnerability Reward Program on March 5; Google shipped a first mitigation that injects a random UUID into bucket names in v1.144.0 on March 31 and a complete ownership-verification fix in v1.148.0 on April 15. No CVE has been assigned. The disclosure is a concrete reminder that managed-inference platforms inherit Python's deserialization risk at the tenant boundary, not just inside a single account.
