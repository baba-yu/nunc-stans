- **Hinahati ng MosaicQuant ang weights sa dense at sparse na 4-bit na bahagi** — Isang papel na nai-post sa arXiv noong June 14 (arXiv:2606.15652, cs.LG at cs.CL) ang nagmumungkahi ng MosaicQuant, isang 4-bit large-language-model quantization scheme na nakatuon sa tensyon sa pagitan ng pag-compress ng dense na bulto ng isang weight matrix at ng matapat na pagpapanatili ng bihirang malalaking-magnitude na outlier na karaniwang pinuputol ng 4-bit grid. Sa halip na bumalik sa isang mixed-precision na format, hinahati ng MosaicQuant ang bawat weight matrix sa isang dense 4-bit base component na humuhuli sa karamihan ng halaga at isang sparse 4-bit residual component na nagbabayad para sa quantization error sa pinaka-sensitibong-sa-error na block, kaya pareho silang nananatili sa 4-bit. Para hindi muling maipasok ng dalawang-bahaging representasyon na ito ang overhead na karaniwang binabayaran ng mixed-precision na pamamaraan, idinaragdag ng mga may-akda ang ZipperEngine, na nagsasama ng sparse residual computation sa dense 4-bit matrix operations sa pamamagitan ng isang overlapped pipeline, na nagpapanatili ng pinag-isang low-bit execution path. Sa mga modelong LLaMA3 at Qwen3, iniuulat na napapanatili ng pamamaraan ang malapit-sa-FP16 na accuracy habang naghahatid ng hanggang 1.24x na speedup kaysa sa 16-bit baseline. Tulad ng anumang resulta mula sa iisang papel, ang mga bilang ay galing sa mga may-akda mismo at naghihintay ng independiyenteng reproduksyon at mas malawak na saklaw ng modelo. Gayunpaman, ang gawa ay isang konkretong datos sa pagsisikap na gawing default ang 4-bit serving para sa memory-constrained na local deployment sa halip na isang lossy na pamalit. [arXiv:2606.15652 - MosaicQuant: Inlier-Outlier Disaggregation for Unified 4-Bit LLM Quantization](https://arxiv.org/abs/2606.15652)

Kinumpleto ng Z.ai (dating Zhipu AI) ang open-weight release ng GLM-5.2, inilipat ito mula sa June 13 subscription preview tungo sa publikong nada-download na Hugging Face weights sa ilalim ng walang-restriksyong MIT license. Vendor-reported ang mga pigura at naghihintay ng independiyenteng replikasyon, ngunit ang release na ito ang nagpapasigla sa apat na nakatulog na hilera mula sa pool. - **Cross-tenant RCE sa Vertex AI SDK sa pamamagitan ng staging-bucket squatting** — Inihayag ng Unit 42 ng Palo Alto Networks noong June 16 ang isang cross-tenant remote-code-execution chain na tinawag nitong "Pickle in the Middle" sa Vertex AI SDK for Python ng Google Cloud (v1.139.0 at v1.140.0). Kapag inalis ng developer ang isang staging bucket, gumawa ang SDK ng isang deterministikong default na pangalan (project-id-vertex-staging-region) at bineripika lamang na umiiral ang bucket, hindi na pag-aari ito ng tumatawag. Ang isang attacker na nakakaalam ng project ID ng biktima ay maaaring i-pre-create ang bucket na iyon (bucket squatting), kunin ang model upload ng biktima, at ipalit ang isang poisoned artifact. Dahil ang mga Vertex model ay karaniwang sinise-serialize gamit ang pickle o joblib, isang ginawang __reduce__ method ang nagpapatakbo ng arbitrary code sa sandaling i-deserialize ng serving container ng Google ang object, saka kumukuha ng OAuth token mula sa metadata server para sa isang service account na may cloud-platform scope. Iniulat ito ng Unit 42 sa pamamagitan ng VRP ng Google noong March 5; nagdagdag ang Google ng random UUID sa mga bucket name sa v1.144.0 (March 31) at buong ownership verification sa v1.148.0 (April 15). Walang itinakdang CVE. Ginagawa ng 'Pickle in the Middle' disclosure ng Palo Alto Unit 42 noong Hunyo 16 ang isang nahuhulaang default staging-bucket name sa Vertex AI SDK ng Google tungong isang cross-tenant remote-code-execution chain: ang isang umaatake na nakakaalam ng project ID ng biktima ay paunang gumagawa ng bucket, hinuhuli ang model upload, at nagpapalit ng isang lasong pickle na ang __reduce__ method nito ay nagpapatakbo ng arbitrary code sa mismong sandaling i-deserialize ito ng serving container ng Google, tapos kumukuha ng isang cloud-platform-scoped OAuth token. Ito ang pinakamalakas na single-incident na suporta na natanggap ng signed-checkpoint-loader na mga thesis: ang Agent-framework loaders ship signed-checkpoint and manifest mode na prediksiyon (Mayo 11) at ang Open-source serving stacks ship signed-checkpoint loading as default na prediksiyon (Mayo 12) ay parehong tumatarget nang eksakto sa load-time-arbitrary-code na pagkabigong ito, at ang remediation path ng Google - random UUID bucket names, tapos buong caller-ownership verification - ang attested-provenance na postura na parehong hinuhulaan na magiging default. Ang isang nailathalang cross-tenant break ay nagbibigay sa mas malawak na framework cohort ng masisipi na dahilan para ilipat ang artifact trust mula opt-in tungong default, bagaman wala pang agent framework o open serving stack na naglipat ng default na iyon bilang tugon.

Nangingibabaw ang data-platform thread sa lawak. Sa closing day ng Data + AI Summit, muling iniposisyon ng Databricks ang Lakebase bilang unang tunay na LTAP - isang managed serverless-Postgres database na may instant copy-on-write branching at governed agent memory - at pinalawak ang Genie tungong Genie One, isang paid-shaped na coworker suite (Genie Agents, App Builder, Lakeflow Designer, ZeroOps) na may Teams at M365 Copilot beta. Itinutulak din nito ang karamihan ng dormant revivals ngayon. Apat na row ang nabuhay: ang Governed agent-ontology layer hardens into the enterprise-agent moat na prediksiyon (Hunyo 3) sa muling pagtatayo ng Databricks ng governed-context na surface na kinokonsumo ng mga agent; ang Snowflake ships a metered Claude-in-Cortex governed-data agent tier na prediksiyon (Hunyo 2) sa karibal na data platform na naglalabas ng governed, consumption-shaped na agent surfaces; ang Hyperscaler custom AI silicon splits into training vs inference SKUs na prediksiyon (Abril 22) sa inference-dedicated na part ng d-Matrix; at ang AMD Helios plus MI450 commitment book clears 15GW na prediksiyon (Mayo 20) sa isang manipis na banggit sa kalendaryo ng Hulyo 23 Advancing AI na petsa ng AMD.
