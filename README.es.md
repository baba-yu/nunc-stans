- **Una vulnerabilidad crítica de inyección de prompts a RCE en el framework de agentes Langroid (CVE-2026-25879, CVSS 9.8) mantiene la superficie de ataque del SQL agéntico en el foco** -- Una alerta recién publicada fija una calificación crítica de CVSS 9.8 a CVE-2026-25879 en Langroid, un popular framework de código abierto para construir aplicaciones impulsadas por LLM. La vulnerabilidad reside en el SQLChatAgent de Langroid, que ejecuta el SQL producido por el modelo; y como ese SQL es manipulable mediante inyección de prompts, un atacante capaz de moldear la entrada del agente (directamente con un prompt malicioso, o indirectamente envenenando datos que el modelo lee después) puede forzar primitivas peligrosas y específicas del dialecto. Cuando el agente se conecta con un rol de base de datos que tiene privilegios elevados como PostgreSQL `pg_execute_server_program`, MySQL `FILE` o MSSQL `xp_cmdshell`, esas primitivas (por ejemplo `COPY ... FROM PROGRAM`) escalan del robo de datos a la ejecución remota de código completa en el host de la base de datos, según la [GitLab Advisory Database - CVE-2026-25879: Langroid has Prompt to SQL Injection, Leading to RCE](https://advisories.gitlab.com/pypi/langroid/CVE-2026-25879/). La corrección llegó en Langroid 0.63.0, que ahora hace que SQLChatAgent use por defecto una lista de permitidos limitada a SELECT analizada con sqlglot más una lista de bloqueo de patrones peligrosos consciente del dialecto, según la [GitHub Security Advisory - Prompt to SQL Injection leading to RCE in Langroid (GHSA-mxfr-6hcw-j9rq)](https://github.com/langroid/langroid/security/advisories/GHSA-mxfr-6hcw-j9rq) del mantenedor. El patrón es el hilo conductor de la seguridad de la IA agéntica en este momento: la misma ruta de texto-a-SQL-a-base de datos produjo la inyección activamente explotada del proxy de LiteLLM (CVE-2026-42208), donde una cabecera Authorization manipulada llegaba a una consulta de búsqueda de claves sin parametrizar a través de la ruta de gestión de errores; corregida en v1.83.7 y recomendada en v1.83.10-stable, según la [LiteLLM docs - Security Update: CVE-2026-42208 in LiteLLM Proxy](https://docs.litellm.ai/blog/cve-2026-42208-litellm-proxy-sql-injection). La lección que subrayan ambas vulnerabilidades es que cualquier LLM al que se le permita redactar SQL debe ejecutarse contra un rol de base de datos de mínimo privilegio y de solo lectura por defecto, porque la salida del modelo tiene que tratarse como entrada no confiable y controlable por el atacante.
