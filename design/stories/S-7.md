# S-7 — Human and agent operate the same app (Phase E)

Human (generated UI) and `nunc-stans-agent` (MCP) both add rows to
runway-tracker; each sees the other's rows; the metrics view updates;
the strategy read-out quotes only declared metrics. (v1 plan §4,
verbatim.)

The app is `runway-tracker@v1` — built through the real FourFive chat
flow (journey T10's path), frozen and bundled (plan PE11), served by
apps-host at `/apps/runway-tracker/` behind the gate. The agent's tool
surface is exactly the frozen `mcp-tools.json`, gated by the profile's
`skills` allowlist (PE10): the story exercises a granted verb AND a
non-granted tool's refusal. The strategy card's grounding must be a
subset of the declared metric names — checked in code, not by reading
the prose (PE8).

Setup:

    export NS_DATA=$(mktemp -d)      # scratch store, bootstrapped
    # runway-tracker@v1 designed, frozen, bundled into
    #   $NS_DATA/artifact/apps/runway-tracker/versions/001/bundle/
    # a profile for the agents context: provider ollama (or mock for
    # the scripted rehearsal), skills: ["apps:runway-tracker"]
    just up                          # gate :8720 fronts /apps/

Pass (mechanical):

    # human leg — the generated UI
    open http://127.0.0.1:8720/apps/runway-tracker/
      → the manifest-driven screens render (deals, income, cash);
        create one deal row via the form
    $NS_DATA/apps/runway-tracker/data.sqlite exists; the row is in it

    # agent leg — the same app through MCP
    nunc-stans-agent chat  (profile grants apps:runway-tracker)
      → /tools lists runway-tracker_deal_{list,get,create,update,archive}
        (+ the other entities), nothing else
      → ask the agent to list deals: the HUMAN's row comes back
      → ask it to add a deal: runway-tracker_deal_create fires; the
        run-log row carries toolCalls
    reload the generated UI → the AGENT's row is visible to the human

    # metrics update from both writes
    curl :8720/apps/runway-tracker/api/metrics
      → deals_in_discussion reflects both rows; all four T10 metrics
        (monthly_external_income, deals_in_discussion, cash_runway,
        income_concentration) return values, nothing undeclared

    # refusal — tools are allowlisted, not ambient
    under a profile WITHOUT apps:runway-tracker (or against a second
    app not granted): the tool is absent/refused, surfaced verbatim,
    no silent retry

    # strategy read-out grounded only in declared metrics
    /strategy in the app's FourFive session
      → the card renders {win, constraint, risk_to_watch} with the
        version reference runway-tracker@v1 and grounding[] ⊆ the four
        declared names — the subset check is enforced in code; a
        grounding entry outside the declaration FAILS the render

Acceptance is the co-use mechanics, the allowlist refusal, and the
grounding subset — local-model answer quality is not gated (structural
acceptance, the S-11 rule). Evidence (UI screenshots both directions,
terminal transcript incl. the refusal, the metrics JSON, the ai-runs
row with toolCalls) → design/verification/phase-e.md.
