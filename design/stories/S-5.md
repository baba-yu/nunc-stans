# S-5 — Profile stamped through (Phase D)

I create a profile (model + prompt + skills + memory scope), set it as
FourFive's default, and see it stamped in the run log. (v1 plan §4,
verbatim.) The run log asserted here is the **main store's**
`<data store>/runs/ai-runs.jsonl` — FourFive chat and the agent both
write there (plan PD13); pipeline runs stay per-instance and are not
this story's subject.

Setup: scratch store (`NS_DATA=<tmp>`, bootstrapped), `just up`, all
against :8720.

Pass (mechanical):

    # create via the Profiles screen; round-trip through the one door
    curl -s :8720/api/profiles                → lists the new profile
    curl -s :8720/api/profiles/<id>           → {id, name, provider: "ollama",
                                                 model: "qwen3.6:27b",
                                                 system_prompt, skills,
                                                 memory_scope, goal_verify, ui}
    cat  $NS_DATA/profiles/<id>.json          → same JSON (atomic file)

    # the F3 rail is real at the surface, not just in unit tests
    PUT a profile with memory_scope.write ["self/commitment/x"]
                                              → rejected with a clear error

    # default-per-context takes effect without a server restart
    PUT :8720/api/profiles/defaults {"fourfive-chat": "<id>"}
    send one FourFive chat message
    tail -1 $NS_DATA/runs/ai-runs.jsonl       → {caller: fourfive…,
                                                 profile: "<id>",
                                                 provider: "ollama", …}
    switch the default to a second profile in the screen; the NEXT message
    stamps the new id — no restart in between

Duplicate/edit/delete are exercised in the screen while at it (plan T4
acceptance). Evidence (screen screenshots, both ai-runs rows) →
design/verification/phase-d.md.
