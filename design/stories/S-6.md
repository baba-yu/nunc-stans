# S-6 — The loop stops and shows its bill (Phase D)

I send a message with goal-verify ON and an unmeetable goal; the loop
stops at max_iters, reports the unmet gaps, and the cost is visible.
(v1 plan §4, verbatim.)

Two passes (plan PD5): the mechanical one runs on the **scripted mock
judge** — deterministic, zero live tokens; then one small live
confirmation on ollama proves the loop against a real model.

Setup: scratch store, `just up`; a profile whose `goal_verify` names the
mock judge with a scripted never-met verdict sequence.

Pass (mechanical, mock judge):

    # FourFive chat: toggle verify ON on the message, goal =
    # "answer in exactly zero words" (unmeetable by construction)
    send the message
    transcript shows, in order (rendered from the PD5 verify
    boundary events):
      iteration 1 … judge verdict: unmet, gaps: [<non-empty>]
      iteration 2 … judge verdict: unmet, gaps: [<non-empty>]
      loop stopped at max_iters (2)
    the unmet gaps are listed in the transcript, AND
    a cost line shows tokens per iteration + total

    tail -1 $NS_DATA/runs/ai-runs.jsonl → verify: on, verdicts: [
      {met:false, gaps[…], tokensIn, tokensOut},
      {met:false, …}] — one entry per iteration; the token FIELDS
      are present (the mock provider counts zero by nature — real
      cost numbers are the live pass's job; refined at execution)

    # default stays off: the next message WITHOUT the toggle makes
    # exactly one call, verdicts absent

Pass (live confirmation):

    same message under an ollama qwen3.6:27b profile with verify ON →
    the loop visibly runs and stops ≤ max_iters; acceptance is the loop
    mechanics + visible cost, NOT the local model's verdict quality
    (structural acceptance, the Phase C C4 rule).

Evidence (transcript screenshots, the ai-runs rows) →
design/verification/phase-d.md.

First executed: Phase D, 2026-07-07 (see design/verification/phase-d.md
— mock + live passes both PASS; the live loop converged on iteration 2).
